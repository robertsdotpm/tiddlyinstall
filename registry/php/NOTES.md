# PHP catalog notes

Generated by `scrape.py` on 2026-09-17. Re-run it any

## Sources

- Windows binaries: `windows.php.net/downloads/releases/` (current) and
  `.../archives/` (flat historical listing covering 5.2 through the current
  8.x line) plus `museum.php.net/php4/` and `/php5/` for pre-5.2 builds.
  `releases/sha256sum.txt` gives checksums for the currently-active majors
  only; `archives/sha1sum.txt` is a decade-old, 26-line leftover covering
  only 5.2.6-5.2.9, so almost all archived Windows builds have
  `checksum: null` -- the vendor simply doesn't publish one for them anymore.
  Museum listings never published checksums either.
- Source tarballs: `www.php.net/releases/index.php?json&max=1000&version={4,5,7,8}`
  for the version list, dates and checksums (sha256 for modern releases,
  md5 for old ones, `null` for the oldest 4.4.0-4.4.5). Download URL is
  `www.php.net/distributions/<file>`. One entry is recorded per version
  (preferring `.tar.xz`, then `.tar.bz2`, then `.tar.gz` if that's all that
  exists) rather than one per compression format, to avoid tripling the
  catalog for files that are otherwise identical. Per the project brief,
  source is recorded once with `os: "linux"` and covers macOS too (compile
  from source); no macOS-labelled duplicate is created, and source is never
  put in `download_plan.json`.
- Linux/macOS binaries: PHP.net ships none, for any version -- confirmed by
  the absence of any Linux/macOS entry point on php.net/downloads.php. The
  one community option that was cheaply scrapable is `static-php-cli`
  (`dl.static-php.dev/static-php-cli/common/?format=json`), which only goes
  back to PHP 8.0. Its builds are recorded with `variant: "static-php-cli"`
  and a note that they're unofficial; it publishes no checksums. Its `bulk/`
  listing has the same versions with more bundled extensions -- not
  separately cataloged. Its GitHub releases
  (`crazywhalecc/static-php-cli`) are the *build tool*, not prebuilt PHP
  runtimes, so they were not a usable mirror.

## Mirror

`museum.php.net/php{4,5,7,8}/<file>` mirrors `www.php.net/distributions/`
byte-for-byte, but **only for fully end-of-life majors** -- it does not yet
carry the latest patches of still-maintained 8.x lines. That was not
obvious from a small sample (an early 8-file sample looked fine until the
8.5.10 check came back 404), so every source entry's museum equivalent was
HEAD-checked rather than sampling-and-blanket-applying; see `mirrors.json`
for the exact match count and which majors are/aren't covered. For a
handful of pre-5.0 files (`php-4.4.0.tar.bz2` .. `php-4.4.8.tar.bz2` and
similar), `www.php.net/distributions/` itself now 404s -- for those,
`museum.php.net` was promoted from mirror to primary `url` instead of
leaving `size` null.

No working mirror was found for Windows binaries; `mirrors.aliyun.com/php/`
404s and `mirrors.huaweicloud.com/php/` is a JS app with no scrapable
static listing, so neither was pursued further.

## Gaps

- Windows x64 never existed for PHP before the 5.5 line (5.2/5.3/5.4 and
  everything before them are x86-only on Windows) -- recorded as a gap with

- Every major before 8.0 has no Linux/macOS binary at all, official or
  community.
- `windows.php.net/downloads/museum/` (mentioned as a candidate in the
  brief) 404s; `museum.php.net` is the real, working host and was used

## Mirror hunt (2026-09-17)

Extending mirrors per `catalog/MIRROR-HUNT.md`. `catalog/php/extra_mirrors.py`
(new, Python 3 stdlib) applies confirmed mirrors to `releases.json` and every
`download_plan*.json`; it must be re-run after `scrape.py` regenerates those
files (it is idempotent -- re-running just no-ops if mirrors are already
present). Its HEAD-check cache lives in `extra_mirrors_cache.json`.

**Confirmed: `downloads.php.net` mirrors `windows.php.net` completely.**
`windows.php.net/downloads/...` now 302-redirects every request to
`https://downloads.php.net/~windows/...` (a plain Apache/Debian box, not
the BunnyCDN edge in front of windows.php.net) -- `scrape.py` already knew
this as a speed trick (`win_probe`) but never recorded it as a `mirrors[]`
entry. Verified as a *full* mirror (not partial) by HEAD-checking 6 files
spanning old/middle/newest majors (5.6, 7.4, 8.5) and both Windows archs,
all exact matches, then fully downloading one (`php-7.4.33-nts-Win32-vc15-x86.zip`,
24 MB) and confirming its sha256 against the vendor checksum already in
`releases.json` -- matched, then deleted. Since the whole tree redirects,
the mirror was applied to every entry whose `url` starts with
`https://windows.php.net/downloads/` (both `releases/` and
`releases/archives/`): **1370 entries in `releases.json`**, including all
6 Windows entries in `download_plan_majors.json` (5.6.40, 7.4.33, 8.5.10,
both archs) and 29 in `download_plan.json`. It is https-only for GETs
(plain http 301s to https).

**Rejected candidates:**

- `mirrors.sohu.com/php/` -- serves a correct `Content-Length` on `HEAD`
  (8366326 for `php-4.4.9-Win32.zip`, matching the vendor size exactly)
  but a **truncated, inconsistent body on every `GET`** -- three separate
  downloads of the same URL came back at 106496, 196339 and 184051 bytes,
  none matching each other or the declared length, and a same-named
  source tarball (`php-4.4.9.tar.bz2`) failed its md5 the same way. HEAD
  alone would have looked like a match; only the required full-download
  step caught that it's not usable. Rejected outright, not just left
  partial.
- `mirrors.cloud.tencent.com/php/` -- 404, no `php/` tree at all.
- `mirrors.huaweicloud.com/php/` -- re-checked per the brief's hint to try
  direct file URLs instead of the listing page: still no good. Direct
  file paths (both a Windows zip and a source tarball) return HTTP 200
  but the body is an HTML/WAF shell page (`Set-Cookie: HWWAFSE...`,
  `Content-Type: text/html`), not file bytes. Confirms the earlier
  "JS app" finding a different way.
- `crazywhalecc/static-php-cli` GitHub releases -- checked per the brief's
  hint. Its release assets are named `spc-<os>-<arch>.{tar.gz,exe}` (the
  `spc` build-tool binary itself, ~4-5 MB) which is a different file from
  the `php-<version>-cli-<os>-<arch>.tar.gz` *compiled PHP* tarballs on
  `dl.static-php.dev` that the catalog tracks (~13-16 MB). Not a mirror of
  what we need; the four static-php-cli entries in
  `download_plan_majors.json` remain without a mirror.
- Internet Archive / Wayback Machine -- both `archive.org/wayback/available`
  and the CDX API returned HTTP 429 (rate limited) or timed out on every
  attempt this session, for both windows.php.net Windows builds and
  dl.static-php.dev tarballs. Not confirmed either way; worth another pass
  later with more spacing between requests, since it's the natural
  candidate for the still-unmirrored 8.1-8.5 source tarballs and the
  static-php-cli builds.
- `downloads.php.net/~windows/releases/sha256sum.txt` etc. were not
  re-probed as a *separate* mirror target since they're on the same host
  already confirmed above.

**Coverage: releases.json 300/2277 (13.2%) -> 1670/2277 (73.3%) with >=1
mirror. `download_plan_majors.json` 0/11 -> 6/11 (54.5%) -- the 6 Windows
binary entries now have the downloads.php.net mirror; the 4
static-php-cli entries and the museum-only 4.4.9 Windows zip still have
none. `download_plan.json` 0/56 -> 29/56 (51.8%).**

## Mirror hunt round 2 (2026-09-17)

Extending the round-1 mirror hunt per `catalog/MIRROR-HUNT-2.md`. Re-derived
the exact unmirrored set from `releases.json` with a script rather than
trusting `unmirrored-summary.txt` blindly; it matched (470 entries).

**static-php-cli (338 entries, was the largest php gap): now mirrored.**
`dl.static-php.dev` 302-redirects every request through `/down?path=...` to
`https://static-php-cli.fra1.digitaloceanspaces.com/static-php-cli/common/<file>`
-- a DigitalOcean Spaces bucket in Frankfurt. This is the actual object
store behind the CDN, not a separate copy, so it was recorded as a "full
(alias)" mirror rather than an independent one (same convention used for
R's `cdn.rstudio.com`/`cdn.posit.co`). Confirmed by HEAD Content-Length
match on all 338/338 entries (not just a sample) spanning PHP 8.0.30
through 8.5.8, linux/macos, amd64/arm64. static-php-cli publishes no
checksums for these builds (still true, re-confirmed), so no hash-verified
sample was possible. Applied via `tools/add_mirrors.py`
(`php_spc_updates.jsonl`, one line per entry) rather than
`extra_mirrors.py`, since it's a straightforward host-and-path-prefix swap
with no partial-match risk once the prefix was confirmed template-wide;
`extra_mirrors.py` should still gain this template so a re-run after the
next `scrape.py` doesn't lose it (see TODO below).

Leads chased per the brief and their outcome, so a future pass doesn't
re-try them:
- `crazywhalecc/static-php-cli` GitHub Actions artifacts / the
  `static-php/hosted` repo's `download-cache.yml` workflow -- this mirrors
  *other projects'* sources into the CDN (the reverse direction), not a
  place static-php-cli's own build output is re-served from independently.
  No usable lead.
- static-php.dev's own docs guide page was checked directly: no mention of
  an Aliyun or any other alternate host for prebuilt binaries (a search
  result's summary claiming an "Aliyun mirror... recommended" did not
  match anything on the actual page -- treat that claim as wrong).
- `registry.npmmirror.com/-/binary/{php,static-php-cli,static-php,spc}/`
  -- all 404 `[NOT_FOUND]`; npmmirror does not carry this ecosystem.
- Content-stability concern from the brief: not an issue for the mirror
  above since it IS the origin (see mirrors.json note), but worth flagging
  that this doesn't tell us whether static-php.dev *itself* ever rebuilds
  a given version's file in place -- only that whatever it currently
  serves, the Spaces bucket serves identically, by construction.

## Real-app fidelity (installer-builder, 2026-09-19)

Checked with installer-builder's `tests/fidelity/php` (mbstring, pdo_sqlite,
curl and openssl over HTTPS, gd, intl, zip, xml, json and a list of common
extensions) and `tests/fidelity/php-composer` (Composer installing psr/log and
symfony/polyfill-ctype).

- **Windows:** the recipes turned on only openssl, mbstring, curl (and zip on
  8.x). They now also turn on bz2, exif, fileinfo, ftp, gd (gd2 before 8.0),
  gettext, intl, mysqli, pdo_mysql, pdo_sqlite, sockets, sodium (7.2+),
  sqlite3 and xsl, the set a Linux distribution's PHP packages give (every
  name checked against the ext/ folder of the 8.5, 7.4 and 5.6 zips). PHP's
  OpenSSL streams on Windows check certificates against the Windows store,
  but its libcurl has no CA bundle ("SSL certificate OpenSSL verify result:
  self-signed certificate in certificate chain"): the recipes copy the
  policy's `cacert.pem` (curl.se's dated Mozilla bundle) into the runtime and
  set `curl.cainfo`.
- **Composer** is now in the plans: the policy's extra file `composer.phar`
  (2.10.3 for PHP 7.2.5+, 2.2.30 LTS before; SHA-256 as getcomposer.org
  publishes it), for apps that install something, copied into the runtime
  folder by a twin of each recipe; the `composer` install rule runs the
  recipes' `project_install`.
- **Linux and macOS (static-php-cli):** the catalogue keeps the `common`
  builds. They lack intl, sodium, readline, xsl, opcache and apcu. The only
  fuller prebuilt set, `bulk` (and glibc `gnu-bulk`, Linux only), has intl,
  sodium, xsl, readline, opcache, apcu, imagick, swoole and more, but no
  pdo_sqlite or pdo_pgsql, and is 2.5x the size (30 MB against 12 MB for
  8.5.8 Linux x86_64). pdo_sqlite has no pure-PHP replacement, while intl and
  sodium do (symfony/polyfill-intl-*, paragonie/sodium_compat), so `common`
  is the better default. A static build with both would have to be built by
  us with static-php-cli's `spc`.
